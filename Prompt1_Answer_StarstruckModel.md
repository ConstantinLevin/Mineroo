## Evaluating RunPod Queue-Based (QB) Serverless Semantics

RunPod offers two distinct serverless paradigms: Load Balancing (LB) endpoints, which route incoming traffic directly to available workers, and Queue-Based (QB) endpoints, which place requests in a managed buffer to be processed sequentially [cite: 1]. Your current infrastructure relies on the LB model, which behaves similarly to User Datagram Protocol (UDP) networking by dropping requests when overloaded or when a worker takes longer than two minutes to respond [cite: 1]. Shifting to the QB model resolves this architectural mismatch, acting more like Transmission Control Protocol (TCP) by guaranteeing request retention during worker initialization.

### Queue Survival, TTL, and Cold Starts

A critical concern for batch processing is whether queued jobs survive the aggressive 8-minute cold start required to pull a 20 GB Docker image and initialize the vLLM engine. Under the QB model, jobs absolutely survive arbitrary cold starts because they are held safely in the endpoint's queue rather than by the worker itself.

The lifespan of a job is governed by the Time to Live (TTL) parameter, which defaults to 24 hours but can be configured up to 7 days [cite: 2, 3]. Crucially, the TTL timer begins the moment a job is submitted and covers both the time spent waiting in the queue and the execution time [cite: 3]. If you submit a burst of 15 documents and the system takes 8 minutes to spin up a worker, those jobs will patiently sit in the `IN_QUEUE` state. The maximum queue depth is strictly defined as 100 times your configured `max_workers` limit; for example, an endpoint with a maximum of 10 workers can safely buffer 1,000 pending API connections [cite: 4]. 

Once a worker picks up the job, a secondary timer, the `executionTimeout`, takes over. This defines the maximum duration a single job can actively run, defaulting to 10 minutes but also configurable up to 7 days [cite: 2, 3]. If a document requires 20 minutes to parse, you must explicitly override this execution timeout in your request policy to prevent the worker from terminating the job prematurely [cite: 3].

### Interaction Patterns: /run, /status, and Webhooks

To interact with a QB endpoint, the orchestration logic shifts from synchronous HTTPS POST requests to asynchronous job submission. 

Submitting a payload to the `/run` endpoint returns an immediate 200 OK response containing a unique Job ID, rather than blocking until the OCR task completes [cite: 3]. RunPod also offers a `/runsync` endpoint, but this defeats the purpose of asynchronous batching and is susceptible to client-side HTTP timeouts. To retrieve results, a local script can periodically poll the `/status` endpoint using the Job ID. However, the most robust and sanctioned pattern for large batches is to utilize Webhooks. By passing a `webhook` URL in your initial payload, RunPod will automatically send an HTTP POST to your receiving server once the job completes [cite: 3]. If your server fails to acknowledge the webhook with a 200 status code, RunPod will retry the delivery up to two additional times with a 10-second delay [cite: 3]. 

### SDK Maturity and Async Handlers

The user requested an evaluation of handler SDK maturity (async handlers, concurrency per worker, maintenance). The RunPod Python SDK inherently supports a `concurrency_modifier` setting that dynamically adjusts concurrency limits, allowing a single worker to process multiple jobs simultaneously. This feature is particularly beneficial for maximizing GPU utilization during I/O-bound tasks like downloading external PDFs [cite: 5, 6]. 

The SDK officially documents support for `asyncio` via `async def` handlers to process operations concurrently. However, maintenance and stability are immediate concerns: as of late 2024 (Issue #387), there is a confirmed, unaddressed bug where executing an asynchronous handler throws a "coroutine was never awaited" runtime warning, causing the handler to fail and exit with code 0 without processing the payload [cite: 7]. This lack of timely maintenance on critical async features poses a tangible risk if your implementation relies on native Python coroutines inside the handler.

### Payload Limits and Large I/O Patterns

Because MinerU processes heavily degraded, multi-page PDFs, I/O (Input/Output) handling is a major constraint. RunPod imposes a strict 30 MB size limit on both request and response payloads [cite: 1]. If you attempt to base64-encode a 200-page scanned document, you will likely breach this limit.

The sanctioned architectural pattern for circumventing this restriction relies on external storage. Instead of passing the document directly, your thin client should upload the PDF to an S3-compatible storage bucket (such as Amazon S3, Cloudflare R2, or EU-localized MinIO) [cite: 8]. The JSON payload sent to RunPod then simply contains the secure URI (Uniform Resource Identifier) of the document. The Python worker fetches the document, performs the MinerU OCR, uploads the resulting text or JSON structure back to the S3 bucket, and returns the output URI in the RunPod response [cite: 8, 9]. Alternatively, RunPod Network Volumes can be used, though S3 is generally preferred for stateless, high-throughput external transfers [cite: 9].

### Worker Reliability and Fitness Checks

The fragility of workers being killed during initialization is a known pain point. In the RunPod Python SDK, the platform has introduced "Worker Fitness Checks." These checks allow you to validate your worker environment at startup before it officially begins processing jobs [cite: 10]. If the vLLM engine fails to load into VRAM (Video Random Access Memory) or the model weights are corrupted, the fitness check fails, the worker exits with code 1, and it is marked unhealthy before it can ingest and subsequently drop a billable job [cite: 10]. Furthermore, if a worker crashes mid-job due to an Out of Memory (OOM) exception, the QB system has automatic retry semantics built into the queue, attempting to reprocess the job [cite: 1, 11].

### Demystifying the Scale-to-Zero Cost Trap

Your observation that "scale-to-zero is NOT automatic cost-zero" touches on the most common billing trap in serverless GPU architectures. RunPod offers two distinct worker classes: "Active" workers, which bill 24/7 regardless of usage at a 40% discounted rate, and "Flex" workers, which scale to zero but incur full per-second costs when running [cite: 12]. 

**Billed Active Seconds:** Under the QB model, the billing stopwatch begins the moment the Flex worker container starts initializing. This means the 45-95 seconds typically required for the instance allocation, Docker image pull, and VRAM loading are entirely billable [cite: 13, 14, 15]. Conversely, time spent by a job waiting strictly `IN_QUEUE` before a worker is assigned is free [cite: 16].

If you are using Flex workers but still experiencing ghost billing, the culprit is the `idle_timeout` parameter. By default, after a worker completes a job, it remains active for 5 seconds waiting for the next request in the queue [cite: 2, 17]. Billing continues ticking until this timeout expires. If this idle timeout is manually extended (e.g., to 10 minutes) to avoid the 8-minute cold start penalty for subsequent jobs, you are billed for every second the worker sits idle [cite: 17, 18]. Additionally, if `min_workers` is set to any integer greater than zero, those specific workers will stay permanently warm, actively draining your budget even when the queue is completely empty [cite: 18]. To achieve true zero-cost idle states, `min_workers` must be 0, and `idle_timeout` must be kept extremely brief, accepting that sporadic traffic will incur the cold start penalty [cite: 18].

### FlashBoot on QB: The Cold Start Reality

RunPod explicitly supports its "FlashBoot" technology for Queue-Based serverless workloads, claiming sub-500ms initializations. However, FlashBoot primarily operates as a hot-cache optimization. It significantly accelerates the *instance allocation* phase, but it does not bypass the 30-60 second Docker image pull for new containers that have not yet cached your heavy image [cite: 14, 15, 19]. Thus, while the underlying VM boots instantly, a full H100 or A4000 cold start with a 10GB-20GB Docker image will still routinely take 45-95 seconds on RunPod [cite: 14, 15].

### Mitigating the 8-Minute Cold Start: Model Caching

Baking a 1.2B-parameter model directly into your 20 GB Docker image is the primary driver of your 8-minute cold start. RunPod has recently shipped a "Cached Models" feature that directly targets this exact bottleneck. By moving the Hugging Face model weights to a persistent RunPod Network Volume mounted at `/runpod-volume/huggingface-cache/`, the worker skips the massive network download and model extraction phases entirely [cite: 20, 21]. The Docker image shrinks to only contain the MinerU code, PyTorch, and vLLM dependencies. When the container boots, it loads the model offline directly from the high-speed NVMe (Non-Volatile Memory Express) network volume, drastically reducing the cold start from several minutes to a fraction of the time [cite: 20, 21].

**Logistical Execution:** To populate that volume with a 1.2B parameter model before the workers spin up, you must deploy a temporary persistent RunPod GPU/CPU pod mounted to the exact same network volume. Use this persistent pod to execute a one-off setup script that downloads the Hugging Face weights into the designated cache directory. Once the download completes, terminate the persistent pod and point your scale-to-zero serverless endpoint at the populated volume.

## Competing Serverless-GPU Platforms (2026 State)

While RunPod's QB model addresses your mechanical issues, the wider 2026 serverless market offers alternative platforms that natively handle queuing, custom containers, and scale-to-zero economics. However, your hard requirement for EU/EEA data residency acts as a severe filter. 

### The Data Residency Filter (The "Modal" Problem)

Many modern platforms offer EU compute regions, but this is often a superficial compliance layer. True data residency requires that compute, storage, memory snapshots, and telemetry all remain within the European jurisdiction to satisfy GDPR Chapter V cross-border data transfer safeguards [cite: 22, 23]. 

A prime example is **Modal**. While Modal is highly regarded for its developer ergonomics and sub-second cold starts, it fundamentally fails strict EU data residency requirements. Regardless of whether you select an EU compute region, all function inputs, outputs, and telemetry are hard-routed through Modal's centralized control plane located in `us-east-1` (Virginia, USA) [cite: 24, 25, 26]. Transmitting unredacted German tax documents through a US-based control plane, governed by the extraterritorial reach of the US CLOUD Act, exposes the deployment to severe GDPR violations [cite: 22, 27].

### Synthesis of Platform Viability

If you choose to migrate away from RunPod, **Baseten** and **Cerebrium** represent the most robust alternatives. Baseten's native `/async_predict` queue perfectly mirrors your requirement for batch OCR, absorbing cold starts cleanly without client-side timeouts, while passing strict EU InfoSec audits [cite: 22, 28, 31]. Cerebrium offers arguably the best cold-start technology in the industry via container memory snapshotting (2-4 seconds), which could effectively neutralize the pain of loading the 1.2B MinerU model entirely [cite: 37, 39, 40].
